投递分析 岗位分析
真实起点

我在秋招中需要反复根据 JD 调整简历。直接与大模型对话时，每次都要重新提供经历背景，模型也可能把“相关”扩写成“做过”。项目因此从个人效率工具开始，逐步收敛为一个问题：如何让模型只在私人事实边界内回答，并让证据、状态与失败可被追踪？

问题如何演化

项目价值不是起点够不够宏大，而是能否根据真实问题修正方案。

01
重复提供背景每个 JD 都重新解释经历，对话记忆不稳定。
02
结构化事实库为经历分配 fact ID、摘要、边界与风险。
03
引入检索尝试减少上下文与无关事实，但出现漏召回和误召。
04
增加工程边界用校验、哈希、trace、timeout 和 fail-closed 约束后果。
05
回到简单基线数据规模很小时，重新验证完整上下文是否更合理。

当前决策

11 条事实时，完整上下文是更强的默认基线。它的有用精度为 70.7%，keyword 为 70.0%；在几乎不降低精度的前提下，大幅减少了漏召回。因此不再把“必须先 RAG 裁剪”当成先验结论。

但不等于交给模型全选

完整上下文选了 41 项，keyword 只选 20 项；模型也会把“部分支持”分类得过强。完整可见解决了漏召回，没有解决选材和真实性决策。

边界：这是单次、5 份 JD 的方案选择实验，标签来自可审计基线，不是候选人 ground truth、统计 benchmark 或简历通过率证据。本轮 61 条生成表述经逐条审阅未发现明显越界，但该审阅不是候选人确认或形式化保证。

关键问题与回答

先讲判断，再讲框架；不把技术名词当成业务价值。

如果固定流程能完成任务，为什么还要 Agent？

固定的 JD 匹配、选材和 PDF 生成不需要 Agent。Agent 只用于处理开放式、多轮的事实问答，例如“哪些经历能支持这项要求”和“上一轮回答为什么没通过校验”。

模型负责理解与解释，不负责事实授权和最终交付。

为什么使用 LangChain 和 LangGraph？

LangChain 提供消息、模型和 tool calling 接口，但是可替换的适配层，不是项目成果。LangGraph 将 retrieve → generate → verify → reflect 建模为显式状态图，便于条件分支、checkpoint 和节点 trace。

当前节点数不多，纯 Python 状态机也能完成；选用 LangGraph 是为了实践可恢复和可观测的 Agent 工程，不是声称业务离不开框架。

每次直接附上完整事实 Markdown，会不会更好？

对当前 11 条事实，实验显示它是更强的默认基线：覆盖更高，且未明显降低有用精度。但它会把全部私人事实发送给服务商，平均提示字符约翻倍，且模型会倾向多选。

因此短期优先完整可见 + 确定性边界；事实数量或权限需求增长后，再证明分层索引或语义检索的必要性。

为了秋招做这个项目，会不会显得目的太小？

不回避个人需求。项目的开始是解决重复定制简历和事实失真风险，后续则用 API、状态图、故障处理、评测与溯源去检验一个更一般的问题：如何限制生成式模型能造成的后果。

不宣称已有企业用户、生产 SLA 或提高通过率。自用动机不是缺点，无法说明真实边界才是。

秋招看板和 Agent 是同一个核心功能吗？

不是。飞书同步、投递分析和岗位看板是个人求职运营工具；事实库、检索、校验、会话恢复和溯源是 Agent 工程主线。两者来自同一真实场景，但在架构和 README 中应该明确分层。

从实现中得到的工程教训

这些问题均已影响当前设计，而不是空泛的“生产化清单”。

01

Prompt 不是权限边界

模型可能跳过工具。代码会强制补做检索，未获得证据时阻断生成。

02

校验节点也是模型

Verifier 会返回非法 JSON 或错误判断。严格校验 schema，异常时 fail-closed，不把它包装成数学证明。

03

更复杂的检索不一定更好

Semantic 召回更高但增加明确误召；keyword top-5 在小事实库中又明显漏召回。先建简单基线，再证明复杂度。

04

外部依赖失败是正常状态

LLM 会超时、限流或不可用；工具也会抛异常。有限重试、结构化错误和 trace 比无限自愈更可控。

05

Memory 不等于安全的记忆

Checkpoint 会保存对话和证据，属于私密数据。conversation ID 只隔离状态，不等于身份认证。

06

最安全的流程可能没人使用

A/B/C/D 逐项授权足够严格，但不符合快速投递的节奏。保留为审计模式，不强迫日常流程使用。

短期边界

停止范围漂移，只完成一个可复现、可解释的本地单用户版本。

60 秒项目回答

用于面试开场，后续再根据追问展开。

我在秋招中需要反复根据 JD 调整简历，发现直接与模型对话既要重复提供经历，又容易让模型把相关经验扩写成做过的事。所以我建立了带 fact ID 和边界的事实库，并用 FastAPI 和 LangGraph 实现只读事实 Agent。模型只做理解和建议，检索、哈希、授权与交付由确定性代码约束。实现中我发现模型会跳过工具、verifier 会返回错误格式，检索也会在召回和误召之间权衡，因此加入强制取证、fail-closed、有限重试和节点 trace。这个项目目前是本地单用户工程原型，不声称能提高简历通过率或具备生产 SLA。

建议的简历表述

把框架放在工程决策之后，不使用“生产级”和“提高通过率”。

Truthful Resume Agent｜可审计的简历事实 Agent（个人工程项目）
  • 基于 FastAPI 与 LangGraph 实现受约束的事实问答 Agent，将检索、生成、校验与反思建模为显式状态图；通过 UUID 会话、SQLite checkpoint 和节点级 trace 支持状态隔离、恢复与调用追踪。
  • 将 LLM 限制为只读建议层，使用 fact ID、内容哈希和来源审计阻断无证据措辞；实现模型超时与有限重试、工具异常 fail-closed 及结构化错误返回。
